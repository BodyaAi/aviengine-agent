# AviEngine Agent — Development Rules
...

## Цель документа
Дать строгие, практичные и однозначные правила разработки, чтобы обеспечить **надёжность**, **масштабируемость** и **работоспособность** системы на всех этапах. Приоритет — не идеал, а стабильная работа и предсказуемость.

---

## 1. Основные принципы
- **Надёжность прежде оптимизации.** Первичная цель — рабочая, тестируемая и предсказуемая функциональность.
- **Простота и читаемость.** Код должен быть понятен человеку; сложные оптимизации вводятся только по данным.
- **Явная логика вместо магии.** Побочные эффекты и скрытые зависимости запрещены.
- **Малые итерации.** Изменения делаются маленькими шагами с возможностью быстрого отката.
- **Документированность.** Любое изменение, влияющее на поведение системы, сопровождается обновлением документации.

---

## 2. Правила для AI‑ассистентов и автогенерации кода
- **Приоритет корректности.** Любая автогенерация должна сохранять существующие сценарии и проходить тесты.
- **Запрет на самостоятельные изменения контрактов.** AI не меняет API контракты, схемы данных или формат ответов без явного одобрения владельца продукта.
- **Запрет на агрессивные оптимизации.** AI не предлагает или не внедряет оптимизации производительности без профайлинга и метрик.
- **Обязательные артефакты при изменениях:** описание изменений; список затронутых контрактов; тесты; шаги воспроизведения; план отката.
- **Ограничение прав.** AI не получает и не использует секреты, ключи или учётные данные; такие значения подставляет человек.

---

## 3. Ветвление и рабочий процесс Git
- **Готовая продакшн ветка.** `main`.
- **Интеграционная ветка.** `dev` — единственная интеграционная ветка. Мерж в `main` — только из `dev` после прохождения регрессии.
- **Feature workflow.** Для каждой задачи — отдельная ветка от `dev` с префиксом по типу: `feature/<scope>`, `fix/<scope>`, `chore/<scope>`, `docs/<scope>`.
- **PR правила.** Pull request должен содержать: краткое описание, список изменений, инструкции по ручной проверке, оценку рисков и шаги отката. Подробный чек-лист и шаблон — в `CONTRIBUTING.md` и `.github/pull_request_template.md`.
- **Rebase-only.** Перед открытием PR — `git pull --rebase origin dev`. Мерж в `dev`/`main` — rebase или squash, без merge-коммитов (линейная история).
- **Мёрдж.** Только после code review (минимум 1 ревьюер) и зелёного CI (`.github/workflows/ci.yml`).

---

## 4. Кодстайл, тесты и качество
- **Конфиги.** Каждый модуль имеет свои lint и formatter конфиги; они обязательны.
- **Тесты.** Юнит‑тесты для критичных сервисов обязательны. Интеграционные тесты для API‑контрактов обязательны перед merge в `dev/main`.
- **Code review.** Минимум один ревьюер; ревью фокусируется на корректности, читаемости и рисках.
- **Coverage.** Для критичных модулей поддерживать минимальный порог покрытия; порог определяется командой.

---

## 5. API и контракты
- **Единая точка связи.** Все клиенты (frontend) общаются только через backend API.
- **Документирование контрактов.** Каждый эндпоинт имеет спецификацию (пример запроса/ответа, коды ошибок).
- **Версионирование.** Любые несовместимые изменения API — через версионирование и миграционные инструкции.
- **Тестовые данные.** Примеры запросов/ответов и мок‑сервисы должны быть доступны в репозитории.

---

## 6. Безопасность и секреты
- **Секреты вне репозитория.** Ключи и секреты хранятся в секретном хранилище (env manager, vault) и не коммитятся.
- **Минимальные права.** Сервисы работают с минимально необходимыми правами.
- **Логирование и аудит.** Критичные операции логируются; логи доступны для аудита.

---

## 7. CI CD и деплой
- **Отдельный pipeline для каждого модуля.** backend, frontend имеют свои CI.
- **Проверки в CI.** Lint, тесты, сборка и базовые интеграционные проверки — обязательны.
- **Деплой с откатом.** Каждый релиз имеет план отката и мониторинг после релиза.
- **Feature flags.** Для рискованных изменений использовать feature flags и постепенный rollout.

---

## 8. Мониторинг и метрики
- **Метрики и алерты.** В продакшне должны быть метрики доступности, ошибок и производительности.
- **Профайлинг перед оптимизацией.** Оптимизации вводятся только после измерений и анализа.
- **SLO/SLA.** Критичные сервисы имеют определённые SLO; мониторинг проверяет их соблюдение.

---

## 9. Документация и артефакты
- **README для каждого модуля.** backend/, frontend/ — обязательные README с инструкцией запуска.
- **Docs обновляются вместе с изменениями.** Любое изменение архитектуры или контрактов сопровождается обновлением docs/.
- **Архив скриншотов и Figma‑экспорта.** Скриншоты и экспорт из Figma прикладываются к задачам для контекста.

---

## 10. Чеклист перед merge
1. **Функциональность** проверена вручную.  
2. **Тесты** проходят в CI.  
3. **Документация** обновлена.  
4. **Риски** описаны и есть план отката.  
5. **Секреты** не попали в коммит.  
6. **Метрики** и мониторинг учтены при изменениях, влияющих на производительность.

---

## 11. Строгое соблюдение официальной документации Авито

При разработке строго опираться на документы,
расположенные в папке docs/avito-documentation/.

Эти файлы являются единственным источником истины для:
- структуры запросов
- структуры ответов
- названий полей
- типов данных
- обязательных и необязательных параметров
- доступных эндпоинтов
- правил авторизации

### Запрещено:
- придумывать параметры, поля, эндпоинты или типы данных
- интерпретировать API «по аналогии» или «по логике»
- изменять структуру запросов или ответов
- добавлять необязательные параметры без подтверждения в документации
- использовать API, отсутствующие в docs/avito-documentation/

### Обязательные требования:
- перед генерацией кода бэкенда AI обязан сверяться с PDF и Swagger из docs/avito-documentation/
- использовать только те поля, которые указаны в официальных документах
- при отсутствии информации — запрашивать уточнение, а не фантазировать
- любые изменения API должны быть подтверждены человеком

### Цель:
Гарантировать корректную работу интеграций с Авито и исключить ошибки,
вызванные догадками или автогенерацией.

## 13. Использование референсного прототипа (Legacy website prototype)

Обязанность строго ориентироваться на эталонный прототип,
расположенный в каталоге:

aviengine/docs/legacy_website_prototype/AviEngine\Website/

А так же референсы: 

aviengine/docs/references/reference-style/
aviengine/docs/references/reference-ui/


### Обязательные требования:
- прототип является **эталонной реализацией**, определяющей структуру экранов, навигацию, логику и UX‑паттерны;
- при разработке нового интерфейса обязанность **сохранять структуру и поведение**, реализованные в прототипе;
- переписывание допускает **только замену UI‑компонентов**, но не изменение сценариев, логики или структуры;
- названия файлов, маршрутов, экранов и компонентов должны соответствовать прототипу, если иное не указано явно;
- любые отклонения от прототипа запрещены без прямого указания пользователя.

### Запрещено:
- изменять структуру экранов или навигацию по собственному усмотрению;
- добавлять новые экраны, шаги, состояния или логику, отсутствующие в прототипе;
- удалять существующие элементы, если это не указано пользователем;
- «оптимизировать» или «улучшать» UX без подтверждения.

### Цель:
Гарантировать, что новая версия приложения cайта соответствует исходному прототипу и сохраняет
его поведение, сценарии и пользовательский опыт в улучшенном виде.
