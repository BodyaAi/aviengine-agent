# AviEngine — Architecture

AviEngine — это Web-платформа + backend, которая автоматизирует выкладку объявлений на Авито:  
создание, обновление, уникализацию и Smart‑Migration, строго через официальные API Авито.

---

## High‑level обзор

### Компоненты системы

- **Frontend (Next.js 14 + Tailwind CSS + shadcn/ui)**  
  Лендинг (статика, SEO, быстрая загрузка) и дашборд (защищённые страницы, авторизация) — всё в одном приложении на Next.js App Router.

  OAuth callback от Авито обрабатывается прямо внутри Next.js через `/api/auth/callback/avito` — никаких отдельных серверов для этого не нужно. FastAPI получает уже готовый токен.

  Tailwind CSS обеспечивает точный перенос из Figma в код: `padding: 16px` → `p-4`, `border-radius: 8px` → `rounded-lg`. Никакого отдельного CSS.

  shadcn/ui даёт готовые премиум-компоненты (кнопки, карточки, модалки, таблицы), которые полностью кастомизируются под дизайн AviEngine.

  ```
  Frontend (Next.js 14 App Router)
  ├── /app
  │   ├── page.tsx               ← лендинг
  │   ├── dashboard/             ← дашборд после авторизации
  │   └── api/
  │       └── auth/
  │           └── avito/         ← OAuth callback endpoint
  ├── components/                ← shadcn/ui + кастомные компоненты
  └── tailwind.config.ts         ← цвета и шрифты из Figma
  ```

- **Backend API (FastAPI)**  
  Основная бизнес‑логика, работа с БД, очередями, интеграциями с Авито и AI.

- **Workers**  
  Асинхронные фоновые задачи: публикация, обновление, миграция, анализ и исправление отклонений.

- **Avito Integrations**  
  Официальные API Авито:
  - OAuth (Авторизация)
  - Autoload API (Автозагрузка)
  - (опционально) Listings API для точечных обновлений

- **AI / RAG слой**  
  Уникализация текстов, генерация описаний, помощь в анализе отклонений.

- **Billing & Slots**  
  Учёт слотов (подключённых аккаунтов Авито) и использование AI.

- **Notifications**  
  Уведомления о проблемах и статусах (ошибки публикации, отклонения, авторизация, биллинг).

## Пользовательский поток (как работает сервис)

### Привязка аккаунта Авито (OAuth)

1. Пользователь на сайте AviEngine нажимает кнопку **«Привязать аккаунт Авито»**.  
2. Браузер открывает OAuth‑страницу Авито.  
3. Пользователь даёт разрешение AviEngine.  
4. Авито возвращает `code` → Next.js `/api/auth/callback/avito` получает `access_token` + `refresh_token` и передаёт их в FastAPI.  
5. Backend сохраняет токены и связывает их с **Slot** (слот = 1 аккаунт Авито).

**Зачем:**  
Без этого AviEngine не может публиковать объявления от имени пользователя.

---

### Создание разных объявлений внутри одного шаблона

1. В шаблоне пользователь выбирает аккаунт(ы) для публикаций и города (гео).
2. Пользователь нажимает «Создать объявление» внутри шаблона.
3. Его перекидывает на сайт Авито (в браузере), где он вручную заполняет форму объявления.  
4. AviEngine (через Playwright Recording / аналогичный механизм) **считывает структуру формы**:
   - какие поля есть
   - какие атрибуты
   - какие значения
   - какие категории
   - файлы (фото)
5. Эта структура сохраняется в `recording_meta` у Template/Variant.

**Важно:**  
AviEngine **не автоматизирует действия пользователя**, а только **запоминает структуру формы**, чтобы потом правильно формировать фид.

При добавлении больше 1 объявления (повторное создание с другими параметрами, которые настраивает пользователь) AI автоматически заполняет поля названия и описания уже уникализированными текстами.

---

### Конвертация в фид (Autoload feed)

На основе:

- `Template`
- `Variant`
- `recording_meta`

Backend формирует **фид** (XML/JSON) в формате, который ожидает **Avito Autoload API**.

**Зачем:**  
Autoload работает с фидами, а не с формами. AviEngine превращает заполненную форму в корректный фид.

---

### Запуск AI‑агента выкладки

Когда пользователь «запускает AI‑агента» в менеджере задач на сайте AviEngine, это означает:

- включить автоматическую публикацию фидов через Autoload API  
- включить AI‑unique (уникализацию текстов, уникализацию фото)

---

### Публикация через Autoload API

1. Backend создаёт **PostingTask** для каждого Variant/фида.  
2. **posting_worker** берёт задачу из очереди.  
3. Формирует фид (если ещё не сформирован).  
4. Отправляет фид в **Avito Autoload API**.  
5. Периодически опрашивает статус (success / error / rejected).  
6. Обновляет статус Variant / PostingTask.  
7. В случае ошибок — создаёт **RejectionCase**.

## Обновление объявлений (UpdatesTab)

#### Концепция

Вкладка «Обновления» управляет уже опубликованными объявлениями на Авито.
Обновления выполняются исключительно вручную по инициативе пользователя —
никакого автопилота. Это не изолированный экран — это источник задач
для Менеджера задач.

Конвейер:
UpdatesTab (выбор аккаунта → выбор объявлений → выбор типа обновления)

│

↓

Confirmation Dialog (пользователь видит итог перед отправкой)

│

↓

ManagerTab (задача создана → worker запущен)

│

↓

Autoload API (обновление через фид с явным указанием avito_id)

│

↓

ErrorsSection (ошибки → AI-анализ)

#### Импорт объявлений пользователя

После авторизации через Авито OAuth backend делает запрос к API Авито
и сохраняет объявления пользователя в таблицу `listings`:
GET /core/v1/items → забираем id, title, price, image

Объявления импортируются и отображаются строго в контексте конкретного
аккаунта Авито. Пользователь сперва выбирает аккаунт, затем видит его
объявления. Каждое объявление имеет уникальный `avito_id` — жёсткий якорь
для Autoload API.

#### Типы обновлений (UpdateAction)

Пользователь выбирает не только какие объявления обновить, но и что именно
сделать с каждым из них:

| Тип | Действие | Что происходит |
|---|---|---|
| `ai_text` | AI уникализация текста | LLM генерирует новый заголовок/описание → подставляется в фид |
| `ai_photos` | Уникализация фото | Viktor API обрабатывает фото → новые URL в фиде |
| `upload_photos` | Загрузить новые фото | Пользователь загружает файлы → **на выбор:** тасовать как есть или уникализировать *через Viktor API*| 
| `custom_text` | Свой текст | Пользователь вводит варианты → система тасует по объявлениям |
| `refresh` | Простое обновление | Стандартное обновление без изменения контента |

#### Детали: upload_photos — режимы обработки фото

При выборе вкладки «📁 Загрузить фото» пользователь может загрузить
свои изображения и выбрать **режим обработки** перед применением
к объявлениям:

| Режим | `photo_mode` | Описание |
|-------|-------------|----------|
| **Тасовка (shuffle)** | `shuffle` | Загруженные фото подставляются к выбранным объявлениям как есть, без изменений. Система равномерно распределяет фото между объявлениями. |
| **Уникализация через Viktor API** | `viktor_unique` | Каждое загруженное фото сначала отправляется в Viktor API для генерации уникальной версии (изменение фона, цветокоррекция, микрокомпозиция), затем уникализированные версии подставляются в фид. |

Выбор режима отображается в интерфейсе как переключатель под дропзоной:

```
┌─────────────────────────────────────┐
│  📁 Загрузить фото                   │
│  ┌───────────────────────────────┐   │
│  │  Перетащите файлы сюда        │   │
│  │  или нажмите для выбора       │   │
│  └───────────────────────────────┘   │
│                                      │
│  Режим обработки:                    │
│  ● Тасовка (без изменений)           │
│  ○ Уникализация через Viktor API     │
│                                      │
│  Загружено: 5 фото                   │
└─────────────────────────────────────┘
```

В `update_config` JSON это выглядит так:

```json
// Режим "тасовка"
{ "action": "upload_photos", "photo_mode": "shuffle" }

// Режим "уникализация через Viktor"
{ "action": "upload_photos", "photo_mode": "viktor_unique" }
```

#### Структура таблицы `listings`

```sql

├── user_id

```

#### Тройная защита от слепых обновлений

1. **Контекст вкладки определяет действие.** Пользователь сначала выбирает
   тип обновления, потом отмечает объявления. Интерфейс всегда показывает
   что именно будет сделано с выбранными объявлениями.

2. **Привязка по avito_id.** Backend формирует фид с явным указанием
   `avito_id` для каждого объявления и только тех полей которые нужно
   изменить. Autoload API обрабатывает строго указанные объявления —
   остальные на аккаунте не затрагиваются.

3. **Confirmation Dialog.** Перед отправкой пользователь видит сводку:
   действие, количество объявлений, аккаунты. Только после подтверждения
   создаётся задача в Менеджере задач.

#### Сценарии использования

**Сценарий 1 — AI уникализация текста:**
1. Пользователь выбирает вкладку «🤖 Уникализация текста»
2. Отмечает нужные объявления
3. Подтверждает в Confirmation Dialog
4. В Менеджере задач создаётся задача: *«AI уникализация текста: N объявлений»*
5. update_worker запрашивает AI-уникализацию → формирует фид → Autoload API
6. Карточки → `done` или `error`

**Сценарий 2 — Загрузка своих фото:**
1. Пользователь выбирает вкладку «📁 Загрузить фото»
2. Загружает файлы через дропзону → сохраняются в `uploaded_photos`
3. Отмечает объявления → подтверждает
4. Фид формируется с новыми URL фото → Autoload API

**Сценарий 3 — Свой текст с вариантами:**
1. Пользователь выбирает вкладку «✍️ Свой текст»
2. Вводит 2–5 вариантов заголовка и описания
3. Отмечает объявления → система тасует варианты между ними
4. Фид с распределёнными вариантами → Autoload API

**Сценарий 4 — Ошибка при обновлении:**
1. Объявление не обновилось (429, XML и т.д.)
2. Карточка получает статус `error`
3. Задача в Менеджере задач подсвечивает ошибку
4. ErrorsSection → AI-анализ (см. раздел 2.9)

#### Логика воркера

```python
selected_listings = db.query(Listing).filter(
    Listing.id.in_(selected_ids),
    Listing.user_id == user_id,
    Listing.slot_id == slot_id,
    Listing.last_updated_at < datetime.now() - timedelta(hours=1)
).all()

feed_entries = []
for listing in selected_listings:
    entry = {"avito_id": listing.avito_id}
    action = listing.update_config.get("action")

    if action == "ai_text":
        new_text = ai_uniqualizer.uniqualize(
            title=listing.title,
            description=get_current_description(listing.avito_id)
        )
        entry["title"] = new_text["title"]
        entry["description"] = new_text["description"]

    elif action == "ai_photos":
        entry["images"] = viktor_client.uniqualize(
            images=get_current_images(listing.avito_id)
        )

    elif action == "upload_photos":
        photo_mode = listing.update_config.get("photo_mode", "shuffle")
        if photo_mode == "viktor_unique":
            entry["images"] = viktor_client.uniqualize(
                images=listing.uploaded_photos
            )
        else:
            entry["images"] = listing.uploaded_photos

    elif action == "custom_text":
        variant = get_next_variant(listing.custom_variants, listing.avito_id)
        entry["title"] = variant["title"]
        entry["description"] = variant["description"]

    # action == "refresh" → стандартное обновление без изменений контента

    feed_entries.append(entry)

autoload_api.send_feed(user_id, feed_entries)
```

Ограничение Авито Autoload — не чаще раза в час. Если прошло меньше часа —
карточка показывает «Доступно через N минут».

## AI‑unique (уникализация)

Для Variants типа `ai_unique`:

1. Берётся исходный текст (title/description).  
2. Через RAG + LLM генерируется **лёгкая переформулировка**.  
3. Структура объявления (параметры, категория) **не меняется**.  
4. Новый текст сохраняется в Variant.  
5. Дальше — обычная публикация через Autoload.

## Viktor API (уникализация фото)

AviEngine интегрируется с **Viktor API** — сервисом уникализации изображений.

**Назначение:**
- генерация «уникальной» версии фото для создания большого количества объявлений.

**Как используется в AviEngine:**
- backend отправляет исходные изображения в Viktor API
- получает уникализированные версии и подставляет их в Variant перед формированием фида
- оригиналы могут храниться отдельно для аудита

*Позже информация об API Виктора расширится.*

## TabManager - Technical errors.

Ошибка                           Решение
────────────────────────────────────────────────────────────
429 Too Many Requests            Exponential backoff,
                                 повтор через 30 мин

503 Service Unavailable          Retry × 3, интервал 5 мин

Фид не прошёл валидацию XML      Регенерация фида из Variant

upload чаще раза в час           Очередь с TTL 1 час

access_token истёк               Auto-refresh через
                                 refresh_token, без участия
                                 пользователя

avito_id mismatch                Синхронизация через
                                 getAdIdsByAvItoIds
